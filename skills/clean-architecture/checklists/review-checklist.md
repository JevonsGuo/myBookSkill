# 整洁架构设计与边界审查清单 (Clean Architecture Review Checklist)

> 用于系统架构方案评估、新建模块设计评审、日常 PR 分层合规核对与架构腐化治理。

---

## 📋 架构分层自查清单 (Checklist)

### 一、 依赖方向与分层隔离 (The Dependency Rule)

- [ ] **1. 依赖方向绝对单向朝内**  
  - **判定依据**：内层模块（Entities / Use Cases）源码中严禁出现任何对外层模块（Controllers / ORM / Web框架）的 `import` 语句。  
  - **违背代价/风险**：内层核心业务受外层变动污染，导致系统失去独立演进与替换技术栈的能力。

- [ ] **2. 实体层纯粹性与零框架依赖**  
  - **判定依据**：Entities 层的对象必须是纯纯纯语言对象（POJO / Plain Class），没有任何特定 ORM（如 `@Table`、`@Entity`）或 Web 框架注解。  
  - **违背代价/风险**：领域模型与数据库结构强行 1:1 绑定，关系数据库的范式约束反向绑架业务表达力。

- [ ] **3. 用例层面向端口抽象 (Ports) 编程**  
  - **判定依据**：Use Cases 访问数据库、消息队列或外部三方接口时，只通过自身定义的 Input/Output Port 接口交互，绝不直接 new 或注入外层实现类。  
  - **违背代价/风险**：用例与具体外部依赖强耦合，无法脱离真实网络或数据库环境执行单测。

- [ ] **4. 跨边界数据解耦与禁止实体裸传**  
  - **判定依据**：Controller 向 Use Case 传参使用扁平 RequestModel；向前端响应使用 Presenter 组装的 ViewModel，严禁将 Entity 直接作为 HTTP 响应返回。  
  - **违背代价/风险**：系统内部状态、密码哈希或敏感审计字段随接口意外泄露；前端迫使后端在实体上加序列化黑魔法。

---

### 二、 细节解耦与可测试性 (Details as Plugins)

- [ ] **5. 数据库细节隔离与延迟选型**  
  - **判定依据**：核心业务规则不知晓底层持久化用的是 MySQL、MongoDB 还是内存 Hash 表；适配器层负责领域实体与 ORM 表实体的双向映射。  
  - **违背代价/风险**：更换数据库或做分库分表时，核心业务代码需要大面积重构，测试代价极高。

- [ ] **6. 交付机制与 Web 细节隔离**  
  - **判定依据**：Use Cases 内部决不出现 `HttpServletRequest`、`Response`、`Cookie`、`Session` 或 HTTP 状态码等表现层概念。  
  - **违背代价/风险**：业务用例无法在 CLI 命令行、后台异步任务或非 HTTP 协议（如 gRPC/MQ）中复用。

- [ ] **7. 100% 纯内存独立可测试性**  
  - **判定依据**：所有 Use Cases 能够通过注入内存存根（InMemoryRepository）在 10 毫秒内完成全量业务逻辑单元测试，无需启动任何 Docker 或 DB 容器。  
  - **违背代价/风险**：单测运行缓慢（从秒级变成数分钟），开发者放弃频繁跑测试，TDD 与 CI/CD 流水线失效。

- [ ] **8. 集中式装配根 (Composition Root)**  
  - **判定依据**：所有外部驱动的实例化与依赖注入逻辑，全部集中在 `main` 模块或框架的配置类中完成，业务类绝不自行实例化外部服务。  
  - **违背代价/风险**：外部连接句柄散落各处，依赖关系失控，无法统一切换环境配置或打桩测试。

---

### 三、 架构反模式与边界防御 (Anti-Patterns Defense)

- [ ] **9. 无环依赖原则 (ADP 遵从)**  
  - **判定依据**：组件间的依赖拓扑图是有向无环图（DAG），不存在 A 依赖 B、B 又反向依赖 A 的任何直接或间接闭环。  
  - **违背代价/风险**：产生难以拆解的代码死结，无法单独发布或构建某个子模块，修改极易产生不可预期的雪崩回归。

- [ ] **10. 杜绝伪分层与空转穿透**  
  - **判定依据**：Controller 不包含复杂流程计算与事务逻辑（代码控制在 100 行内）；不存在 Controller 直接绕过 UseCase 裸调 DAO 的现象。  
  - **违背代价/风险**：三层架构沦为名存实亡的形式主义，业务逻辑全部沉沦为胶水代码。

- [ ] **11. 治理万能工具类黑洞 (Utils Black Hole)**  
  - **判定依据**：不存在全系统任意调用的超级 `CommonUtils` 类；共享概念已按领域提炼为值对象（Value Objects）或按边界清晰下沉。  
  - **违背代价/风险**：万能工具类成为全系统隐式强耦合汇聚点，破坏分层隔离边界。

- [ ] **12. 遵循稳定依赖原则 (SDP 遵从)**  
  - **判定依据**：稳定、核心的高层策略模块绝不依赖易变、不稳定的边缘组件（如临时三方 SDK 或前端样式包）。  
  - **违背代价/风险**：易变边缘工具的微小升级，迫使核心稳定业务模块频繁重新编译、测试与发版。

## 📊 架构评审打分标准

| 得分区间 | 状态判定 | 架构健康度建议 |
| :--- | :--- | :--- |
| **12 项全部通过 (100%)** | 🟢 **整洁典范 (Excellence)** | 边界清晰，依赖单向，可测试性极强，具备极高技术弹性。 |
| **通过 10~11 项 (80%~99%)** | 🟡 **基本达标 (Passable)** | 存在局部侵入（如个别 DTO 混用或 Controller 偏重），限期重构治理后上线。 |
| **低于 10 项 (<80%) 或违反红线 (第 1、2、4 条)** | 🔴 **架构腐化 (Blocked)** | 存在边界击穿、循环依赖或实体裸奔，**禁止合并/禁止通过评审**，必须重构分层。 |
