# 03 - 轻量审查形态与人机分工律 (Lightweight Methods & Automation)

## 一、 核心概念与实证准则

- **人机分工铁律（The Automation Rule）**：
  - **凡是能被静态代码检查工具、编译器、Linter、自动化测试发现的问题，严禁浪费人类审查者的时间去人肉排查**。
  - 机器专攻：空格缩进、命名格式、未使用的引用、代码规范（PEP8、ESLint）、简单的静态语法漏洞。
  - 人类专攻：**业务逻辑是否正确闭环、系统架构是否合理、异常分支与并发边界、代码可读性与长期维护性**。
- **5 大同行审查形态全景对比（5 Review Techniques）**：
  1. **工具辅助异步审查（Tool-assisted Review）**：★ *最优主流*。基于 PR/MR 工具，有完备的上下文 Diff、持久化讨论记录与自动化流水线。
  2. **肩并肩走查（Over-the-shoulder Review）**：两人在同一个屏幕前边看边讲。适合新人入职带教或核心复杂模块快速对齐。
  3. **结对编程（Pair Programming）**：编写代码的同时实时走查。成本高，但适用于突破超高复杂度架构难题。
  4. **邮件/聊天消息流转（Email/Chat Pass-around）**：缺点是版本碎片化、讨论断层，不推荐作为主流程。
  5. **形式化会议审查（Formal Inspection / Fagan）**：召集 4~6 人开半天评审会。成本极高且容易陷入低效辩论，除军工航空等特殊领域外应极力避免。

## 二、 审查形态选型决策树 (Decision Tree)

```text
需要组织代码审查
│
├── 1. 自动化流水线前置 (CI Gate)
│   ├── 自动化单测、Linter 与类型检查是否全部通过？
│   │   ├── 否 ──► CI 自动拦截并标记红灯，人类审查者拒绝介入！让机器先挑错
│   │   └── 是 ──► 机器放行，人类介入
│
├── 2. 审查形态选型
│   ├── 新人入职首次提交 / 极其复杂的底层算法设计？
│   │   └── 选用【肩并肩实时走查】或【结对剖析】，15~30 分钟直接当面沟通
│   └── 日常 95% 的业务特性、Bug 修复与接口重构？
│       └── 选用【工具辅助异步审查】（PR / CL 模型），利用结构化工具沉淀历史记录
```

## 三、 人机分工反模式 (Anti-patterns)

- **反模式 1：人肉 Linter（Human Linter Syndrome）**
  - *表现*：审查者在 PR 留下 15 条评论，全是“第 3 行少了一个空格”、“第 10 行变量名应该用下划线不是驼峰”。
  - *危害*：极度浪费专家级工程师的高价值脑力，忽视了真正的业务逻辑深坑。
- **反模式 2：重度会议狂热（The Meeting-Heavy Review）**
  - *表现*：每个小改动都必须拉上全组 8 个人开 1 小时投屏会议。
  - *危害*：全员时间被严重碎片化，会议中大部分人处于神游状态，性价比极低。
- **反模式 3：绕过 CI 直奔人工（Reviewing Broken Builds）**
  - *表现*：代码在本地连 build/test 都不通过就发起审查，让同事帮自己当免费编译器。
  - *危害*：打断评审者思路，严重破坏协作礼仪。

## 四、 Do & Don't 对比

### 场景：配置自动化与人工评审边界

```markdown
<!-- ❌ DON'T: 人肉挑格式，漏看业务逻辑 -->
评审者评论：
"1. 第 12 行换行符多了一个；
 2. 第 18 行 import 未按字母序排列；
 3. 代码格式看起来挺规整的，我 approve 了。"
(结果：代码里的结算公式少算了 10% 佣金，由于无人审业务而溜上生产)

<!-- ✅ DO: 机器拦截格式，人类专注业务与数据流 -->
CI 自动化检查：
- 自动运行 flake8/black/pytest，格式不合格直接阻断 PR 合并。

评审者评论：
"CI 已通过。我重点审阅了 `routes.py` 的业务数据流：
1. 第 44 行结算金额未防范空值字典传入；
2. 异常捕获过于宽泛，建议精确捕获 `DBConnectionError`，避免掩盖逻辑笔误。"
```
