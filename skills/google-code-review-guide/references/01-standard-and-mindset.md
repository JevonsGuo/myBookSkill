# 01 - 审查基准与核心心智模型 (The Standard & Mental Models)

## 一、 核心概念与基准法则

- **最高仲裁准则（The Senior Principle）**：
  > **Reviewers should favor approving a CL once it definitely improves the overall code health of the system, even if the CL isn't perfect.**  
  > 只要变更在整体上明确提升了系统的代码健康度，即便尚未达到完美，审查者也应倾向于批准。
- **持续改进而非追求完美（Continuous Improvement vs. Perfectionism）**：不存在所谓的“完美代码”，只有“更健康的代码”。严禁为了抠微小的修饰性细节，将整体上提升系统的变更拖延数天甚至数周。
- **事实与数据胜于个人偏好（Facts Over Opinions）**：
  - 技术事实、性能测试数据、官方架构规范高于个人主观审美。
  - 针对代码风格（Style），代码规范（Style Guide）具有绝对权威。若规范未做强制要求且无既定约定，尊重作者选择。
  - 软件设计永远不是“纯个人偏好”，必须基于底层工程原则（高内聚、低耦合、信息隐藏等）进行权衡。
- **净增法则（Net Positive Health）**：除紧急救火（Emergency）外，绝不接受任何降低代码库整体健康度的变更。

## 二、 审查决策指南 (Decision Tree)

| 决策场景 | 判定条件 | 评审动作与裁决 |
| :--- | :--- | :--- |
| **设计方案出现分歧** | 作者有数据/工程原则支持，且与评审者方案同等有效 | **接受作者的偏好**，不把个人审美强加于人 |
| **设计方案出现分歧** | 作者方案存在可预见的维护性恶化或违背原则 | **驳回并阐明技术原因**，引用设计原则与长期维护成本 |
| **代码存在优化空间但非致命** | 变更整体提升了系统健康，但存在修饰性小问题 | **批准并打标**：给出建议并前缀 `Nit:`，允许作者决定是否修改 |
| **变更的方向本身存在问题** | 代码要实现的功能系统已决定下线或不属于该库 | **立即礼貌驳回**：不要浪费时间做逐行代码评审，指明替代方案 |
| **双方陷入僵局持续争论** | 通过评论往返超过 2~3 轮仍未达成共识 | **升级沟通**：发起即时语音/面聊；仍无法解决则升级至 Tech Lead / 架构师裁决 |

## 三、 审查反模式与坏味道 (Anti-patterns)

- **反模式 1：吹毛求疵（Nitpicking Blocker）**
  - *表现*：扣住一个变量命名或代码空行不放，强行反复驳回，导致功能交付受阻。
  - *危害*：打击开发者的改进积极性，引发对抗情绪，交付周期拉长。
- **反模式 2：盲目放行（Rubber Stamping）**
  - *表现*：只扫一眼看 diff 不大，直接点击“LGTM”，不看业务逻辑是否正确闭环。
  - *危害*：导致隐蔽的并发死锁、边界漏洞、数据错乱潜入生产环境。
- **反模式 3：对人不对事（Author-targeted Criticism）**
  - *表现*：评论中出现“你为什么写这么蠢的逻辑”、“你难道不知道这个 API 吗”。
  - *危害*：破坏团队协作信任感，阻碍知识传递。

## 四、 Do & Don't 对比

### 场景：指出并发模型使用不当时

```markdown
<!-- ❌ DON'T: 攻击作者、缺乏依据、情绪化 -->
"为什么你要在这里开线程？这里明明根本没必要用并发，你把代码搞得太复杂了！"

<!-- ✅ DO: 对事不对人、阐述技术理由与替代方案 -->
"此处的并发模型增加了系统的复杂度，但从当前数据流看并未带来明显的吞吐收益。
单线程模型反而能避免锁竞争和竞态风险。建议改为单线程顺序执行，代码会更加简洁稳健。"
```

### 场景：提出非阻塞性的建议修饰时

```markdown
<!-- ❌ DON'T: 强制阻塞审批 -->
"这里的方法名我认为改用 executeTransaction() 更好，改了之后我再给你过。"

<!-- ✅ DO: 使用 Nit 前缀明确优先级，不阻碍主线合并 -->
"Nit: 这里的 calculateFee() 内部包含了更新账本的副作用，后续如果方便，考虑提取为 calculateAndRecordFee() 会更明确。本 PR 不强制修改，你可自主决定。"
```
