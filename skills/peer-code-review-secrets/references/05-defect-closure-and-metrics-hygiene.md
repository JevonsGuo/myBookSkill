# 05 - 缺陷闭环验证与度量卫生 (Defect Closure & Metrics Hygiene)

## 一、 核心概念与实证原则

- **修复验证闭环铁律（Verify Every Fix）**：
  - **审查工作绝不是在审查者“提出批注”的那一刻结束，而是在“确认缺陷已被正确修复”后才算闭环**。
  - 实证统计显示：**约 15%~20% 的缺陷修复补丁会无意中引入新的次生 Bug（Secondary Defects）**。
  - 审查者必须复查作者提交的修改 diff，确认问题确实被消灭，且没有破坏周围逻辑。
- **度量卫生与古德哈特定律（Metrics without Dysfunction / Goodhart's Law）**：
  - **“当一个度量指标被用作绩效考核目标时，它便不再是一个有效的度量指标。”**
  - **红线禁忌**：绝对不能把“审查发现的 Bug 数量”或“被提出的批注次数”作为对开发者（作者或审查者）的绩效考评、评优或打分依据！
  - *后果*：若考核审查者找 Bug 数，审查者会狂提 100 条标点空格等琐碎意见刷量；若惩罚被找 Bug 的作者，作者会拼命辩解、掩盖问题甚至绕过审查。
- **度量指标的唯一正确用途：流程与系统改进（Process Optimization Only）**：
  - 采集审查数据（平均审查时长、单次代码规模、高发缺陷类型）的唯一价值，是用于团队的**根本原因分析（RCA）**，以迭代自动化测试套件与检查清单。

## 二、 缺陷修复与验收决策树 (Decision Tree)

```text
作者针对审查意见提交了修复提交 (Fix Commit)
│
├── 1. 修复完整性复核
│   ├── 是否真正根除了原批注指出的逻辑缺陷？
│   │   ├── 否 (只是临时打补丁绕过，未解决根因) ──► 再次指出，要求彻底解决
│   │   └── 是 ──► 见下步
│   │
│   └── 是否附带了针对该缺陷的回归单测？ ──► 强制要求补充针对性测试防回退
│
├── 2. 次生缺陷（Secondary Defects）排查
│   ├── 修改是否修改了外部公共接口签名？ ──► 检查是否会导致其他调用方破坏
│   └── 修改是否影响了事务边界或并发锁？ ──► 审视周围上下文，排查副作用
│
└── 3. 终态批准
    └── 复核完毕且无新坏味道 ──► 给予最终 Approve / LGTM，允许合入
```

## 三、 度量与闭环反模式 (Anti-patterns)

- **反模式 1：提出即放行（Comment and Blindly Approve）**
  - *表现*：审查者写了 5 条严重 Defect 批注，紧接着手滑直接点了 Approve，相信作者“会自动改对”。
  - *危害*：作者可能理解产生偏差，或者改错了导致更严重的死锁，直接合入主干。
- **反模式 2：绩效化考核代码审查（Weaponized Review Metrics）**
  - *表现*：管理者设立 KPI：“每人每周必须提 20 条审查批注”、“代码被提 Bug 最多的人扣绩效”。
  - *危害*：瞬间引发恶性竞争，团队内部技术交流演变为政治斗争，技术质量反而大幅倒退。
- **反模式 3：只见树木不改森林（Symptom-Only Fixing）**
  - *表现*：某类空指针连续出现 10 次，每次都是修具体那一行，从不考虑在脚手架或数据层做全局空值兜底。
  - *危害*：同样模式的低级 Bug 反复在全团队蔓延。

## 四、 Do & Don't 对比

### 场景：复核作者提交的修复代码

```markdown
<!-- ❌ DON'T: 看到有新 commit 就直接点 approve，不复验 -->
作者: "我改好了，你看下。"
审查者: (扫了一眼看到有新 commit) "行，我直接点了，你合并吧。"
(结果：作者把判断条件从 `if not a` 改成了 `if a is not None`，引入了新的空字符串绕过漏洞)

<!-- ✅ DO: 聚焦比对 Fix Diff，确认无次生隐患并要求单测 -->
审查者:
"我仔细复核了你的 Fix Diff（commit abc1234）：
1. 结算金额已正确改为 `Decimal` 并在首行完成了正数断言，原缺陷已解决；
2. 请为这次修复补上刚才讨论的【负数金额用例】单元测试；
3. 测试通过后我立即 Approve。"
```
