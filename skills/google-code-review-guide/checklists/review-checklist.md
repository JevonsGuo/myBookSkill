# Google 级代码审查与业务逻辑验证自查清单

> **使用说明**：本清单由 Google 官方工程审查实践（Google Code Review Developer Guide）浓缩提炼而成。在进行前后端代码扫描、业务逻辑验证或 PR 合并评审时，逐项核对打分。

---

## 一、 功能性与业务逻辑闭环 (Functionality & Logic)

- [ ] **1. 意图达成与双重用户价值**
  - **判定依据**：代码不仅实现了开发者的预定功能，且对最终用户友好、后续维护的开发者易于理解与扩展。
  - **违背代价**：自嗨式实现，功能上线后造成用户操作困惑或被后续开发者误用。
- [ ] **2. 边界条件与非预期输入校验**
  - **判定依据**：所有外部入参（尤其是前端传递的参数）均具备类型、范围、空值、负数、越界的前置校验（Preconditions）。
  - **违背代价**：攻击者绕过前端限制，注入非法数值导致系统报错、金额穿透或死锁。
- [ ] **3. 业务状态机扭转完备性**
  - **判定依据**：所有可能失败的异常分支（如支付失败、网络超时、部分成功）均有明确的状态处理与补偿逻辑，不存在“状态悬挂”。
  - **违背代价**：业务单据卡在中间态，引发财务账目不平或数据孤岛。
- [ ] **4. 并发安全性与竞态防御**
  - **判定依据**：存在共享变量、多线程、异步回调或并发写入时，具备严格的加锁或幂等保护。
  - **违背代价**：高并发下出现幽灵数据更新、重复扣款或死锁事故。

---

## 二、 架构设计与复杂度控制 (Design & Complexity)

- [ ] **5. 架构归属与依赖方向正确**
  - **判定依据**：业务逻辑、接口路由与数据持久化严格分层，无反向循环依赖，不破坏现有模块边界。
  - **违背代价**：产生“大泥球”架构，模块之间高度耦合，牵一发而动全身。
- [ ] **6. 严禁过度设计（YAGNI 准则）**
  - **判定依据**：代码仅解决当前已明确的需求，不存在为“未来假想需求”预留的冗余抽象类、多重工厂或无用参数。
  - **违背代价**：认知负担翻倍，团队长期维护大量无用的“僵尸抽象”。
- [ ] **7. 函数单一职责与自解释性**
  - **判定依据**：函数长度适中，命名清晰直达意图；无需通过阅读长篇注释即可看懂执行流。
  - **违背代价**：代码难以做单元测试，阅读体验极差，修改容易产生意想不到的副作用。

---

## 三、 注释与命名规范 (Comments & Naming)

- [ ] **8. 注释仅解释 Why 而非 What**
  - **判定依据**：注释用于阐明业务折中原因、算法复杂度背景或非显而易见的决策，严禁用来解释写得乱的代码。
  - **违背代价**：代码演进后注释与实现不一致，严重误导未来的维护人员。
- [ ] **9. 命名准确且无歧义**
  - **判定依据**：禁止使用 `data`, `res`, `temp`, `flag` 等无意义命名，使用具体业务语义词汇。
  - **违背代价**：排查问题时无法快速定位变量与函数的真实业务含义。

---

## 四、 测试完整性与代码健康 (Tests & Code Health)

- [ ] **10. 生产变更同包提交测试**
  - **判定依据**：新增或修改的代码逻辑在同一个 PR 中附带单元测试或集成测试，拒绝“后续补测”。
  - **违背代价**：缺乏安全网保护，后续迭代极易发生静默回归（Silent Regression）。
- [ ] **11. 断言真实有效（防伪测试）**
  - **判定依据**：测试包含对具体计算值、业务状态字段的精确 assert，保证在代码被破坏时测试必能报错。
  - **违背代价**：覆盖率虚高，测试形同虚设，无法在重构时提供信心。
- [ ] **12. 逐行通读理解（Review Every Line）**
  - **判定依据**：审查者已完整理解 PR 中被指派审查的每一行代码，无任何盲区或侥幸假设。
  - **违背代价**：藏匿在未细读代码中的低级语法笔误或致命漏洞潜入主分支。

---

## 五、 PR 纯洁度与合入纪律 (PR Hygiene)

- [ ] **13. 小变更单一职责**
  - **判定依据**：变更范围通常在数百行内，只解决一个独立的主题任务。
  - **违背代价**：大 PR 导致审查者注意力稀释（Lost in Detail），审查质量严重下滑。
- [ ] **14. 重构与业务开发严格解耦**
  - **判定依据**：格式化、大面积重命名与新功能开发分别拆为独立 PR 提交。
  - **违背代价**：Git blame 历史被污染，代码冲突解决成本成倍增加。
- [ ] **15. 坚决抵制“先合入后重构”推脱**
  - **判定依据**：凡是引入新缺陷或技术债务的代码，必须在本次 PR 中修正完毕后才可点击 Approve。
  - **违背代价**：“以后改”变成“永远不改”，系统质量逐渐滑坡。
