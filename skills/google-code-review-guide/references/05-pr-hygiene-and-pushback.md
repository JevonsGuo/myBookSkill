# 05 - PR 治理、小变更拆分与推脱拦截 (PR Hygiene & Handling Pushback)

## 一、 核心概念与审查标准

- **小变更原则（Small CLs Rule）**：
  - **一个 CL 应该只解决一件事（One Self-contained Change）**。
  - 通常 ~100 行是理想范围，超过 1000 行通常过大。
  - **审查者有权直接拒绝过大的 PR**：“代码太长无法有效审查，请拆分后再提”。小变更审查速度快、审查更透彻、合入冲突少、更容易排查 Bug。
- **重构与业务解耦（Separate Out Refactorings）**：
  - **严禁把纯重构（改名、移动文件、格式化）与业务功能开发或 Bug 修复混在同一个 PR 里**。
  - 必须拆为两个 PR：先提纯重构 PR 并合入，再提基于重构后的业务逻辑 PR。
- **识破“以后再改”陷阱（The "Clean It Up Later" Trap）**：
  - 作者常说：“*这次先合入，我下个 PR 马上重构/补测试*”。
  - **现实规律**：除非作者**紧接着立刻**提交下一个 PR，否则一旦合并上线，由于日常繁重的工作，这个承诺 95% 以上会永远被遗忘。
  - **原则**：如果引入了新的复杂度或缺陷，必须**现在**改完；绝不允许以此为借口降低代码健康度。
- **评论级别标签化（Label Comment Severity）**：
  - 必须对审查意见清晰定级，避免作者把所有建议都误当作强制阻塞项：
    - `[Blocker]`: 严重逻辑缺陷或破坏性问题，必须修复后才能合入。
    - `Nit:`: 微小修饰（格式、拼写、简单命名），作者可选择性修改，不阻碍合入。
    - `Optional:` / `Consider:`: 审查者的架构思考建议，由作者权衡决定。
    - `FYI:`: 知识分享或扩展参考，本 PR 无需任何动作。

## 二、 变更拆分与异议处置决策树 (Decision Tree)

| 变更特征 / 场景 | 审查判定 | 处置策略 |
| :--- | :--- | :--- |
| **PR 涉及 30+ 文件，包含数据库表、后端 API、前端 UI、代码格式化** | 典型大泥球 PR | **直接退回并建议拆分**：按水平分层（DB/API/UI）或按功能垂直切片 |
| **同一个 PR 里既修改了业务，又把整个文件 500 行做了缩进与重命名** | Diff 严重污染 | **要求剥离**：将格式化/重命名抽取为独立的 Refactor PR |
| **作者抗辩：“赶上线，这次先不加单测，后续补”** | 违背同包测试底线 | **除非系统发生 P0 级线上故障（Emergency），否则坚决驳回**，要求补齐测试 |
| **作者给出合理理由且有实际数据反驳审查者** | 作者对具体业务边界更清楚 | **审查者坦诚接纳**，感谢作者解释并关闭该意见 |

## 三、 审查沟通反模式 (Anti-patterns)

- **反模式 1：疲劳妥协（Reviewer Fatigue Yielding）**
  - *表现*：作者死缠烂打反复推脱，审查者懒得继续争论，无奈点击 Approve。
  - *危害*：技术债务的闸门一旦打开，团队的代码底线将不可逆地滑坡。
- **反模式 2：评论无分级，全员焦虑（Unlabeled Comment Storm）**
  - *表现*：审查者留了 30 条评论，其中 28 条是标点和拼写建议，作者误以为需要推倒重来。
  - *危害*：极大挫败开发信心，沟通成本急剧膨胀。
- **反模式 3：线下私聊定论无沉淀（Unrecorded Offline Decisions）**
  - *表现*：两人面聊达成了某种方案妥协，但 PR 评论区没有任何说明，未来读者完全看不懂为什么代码这么写。
  - *危害*：上下文丢失，代码设计意图成为未解之谜。

## 四、 拆分变更的实战范式 (Splitting Grid)

当面临一个大型全栈需求（例如增加一个新的结算渠道核对）时，应拆解为相互独立的细粒度 PR 网格：

```text
               垂直切片 1: 基础校验与数据模型         垂直切片 2: 完整结算状态流转
            ┌─────────────────────────────┐   ┌─────────────────────────────┐
前端 (UI)   │ PR-4: 添加表单展示与输入框  │   │ PR-5: 结算触发与状态提示    │
            ├─────────────────────────────┤   ├─────────────────────────────┤
接口 (API)  │ PR-2: 新增校验路由与入参    │   │ PR-3: 新增结算执行回调路由  │
            ├─────────────────────────────┤   ├─────────────────────────────┤
核心模型    │ PR-1: 数据表结构与 Proto/DTO│   │ (复用 PR-1 的数据模型)      │
            └─────────────────────────────┘   └─────────────────────────────┘
```
* **收益**：每个 PR 仅百余行，审查者 5 分钟即可审完，Bug 暴露几率降低 80% 以上。
