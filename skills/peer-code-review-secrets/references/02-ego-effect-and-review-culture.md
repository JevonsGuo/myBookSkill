# 02 - 自我效应心理学与团队审查文化 (Ego Effect & Culture)

## 一、 核心概念与心理学机制

- **自我效应（The Ego Effect）**：
  - SmartBear 研究发现，代码审查最具杀伤力的收益之一发生在**提交审查之前**：
  - **仅仅是“知道我的代码会被同行逐行审阅”这一心理预期，就会促使作者在点击提交前，主动自发地重新审查并修正大量低级失误**。
  - 这种预期自我修正（Self-Correction）在日常开发中拦截了超过 50% 以上的代码笔误。
- **作者导读机制（Author Guided Tour / Pre-Review Annotations）**：
  - 在邀请他人审查前，作者应主动提供简明的变更背景、核心改动文件指引与风险点提示。
  - 遇到非显而易见的逻辑或妥协折中，**作者在 PR 评论区预先打上批注**（如：“*注意：第 45 行此处特意捕获特定异常，是为了防范第三方旧接口超时...*”）。
  - 导读机制能使审查者的阅读理解效率提升 30% 以上。
- **心理安全感与去个人化（Psychological Safety & Depersonalization）**：
  - 代码审查是**针对代码的协同改进**，绝非**对开发者个人智商或能力的考核**。
  - 营造“暴露缺陷值得庆幸”的正向氛围：在合并前发现 Bug 越早，生产损失就越小。

## 二、 提交前准备与沟通决策树 (Decision Tree)

```text
开发者准备提交 PR
│
├── 1. 自我效应初检 (Self-Review Before Submit)
│   ├── 自己是否在 Diff 工具中逐行通读过一遍？ ──► 否：立即自读，往往能抓住 3~5 个调试残留或死代码
│   ├── 单元测试是否在本地全部绿灯通过？ ──► 否：严禁提交半成品阻断他人
│   └── 是否留存了 TODO、临时 print 或未使用的引用？ ──► 否：清理完毕后再发 PR
│
├── 2. 提供作者导读 (Guided Tour)
│   ├── 核心改动集中在哪 1~2 个关键文件？ ──► 在 PR Description 中高亮指出
│   └── 是否包含非直观的算法/折中？ ──► 提前在对应行主动留言阐述 Why
│
└── 3. 邀请合适评审者
    └── 指定 1~2 位对该模块最熟悉的同行，避免无目标群发“所有人随意看看”
```

## 三、 审查文化反模式 (Anti-patterns)

- **反模式 1：丢包不管（The Fire-and-Forget Dump）**
  - *表现*：写完代码直接开个 PR，标题只有一个“fix bug”，内容空空如也，直接指定他人。
  - *危害*：审查者毫无上下文，需要从零猜测作者意图，沟通成本倍增。
- **反模式 2：防御性对抗（Defensive Territoriality）**
  - *表现*：一旦评审者指出问题，作者立刻感到自尊受挫，每一条评论都极力争辩“我这里没问题”。
  - *危害*：把技术研讨上升为人际冲突，阻碍团队知识共享。
- **反模式 3：老大哥阴影（The Big Brother Syndrome）**
  - *表现*：管理层把代码审查中的批注数量当做“开发者水平低、经常写 Bug”的考核依据。
  - *危害*：瞬间摧毁团队信任，导致开发者避重就轻、甚至暗中跳过审查流程。

## 四、 Do & Don't 对比

### 场景：作者提交复杂变更时的导读

```markdown
<!-- ❌ DON'T: 零上下文、无导读、无任何预告 -->
PR Title: "update routes"
PR Body: (空)

<!-- ✅ DO: 清晰导读、核心文件指引、主动标注特殊点 -->
PR Title: "feat(settlement): 增加美团新渠道核对逻辑与状态流转"
PR Body:
"### 背景
适配美团 2026 新结算规范。

### 导读建议
1. 请先看 `rule_group_resolver.py` 中的规则解析，这里定义了美团特有的手续费扣减模型；
2. 重点审视 `routes.py` 第 44 行的幂等检查逻辑；
3. 本 PR 包含 6 个新增单元测试，均已在本地执行通过。"
```
