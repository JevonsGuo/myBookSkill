# 代码坏味道扫描与安全重构落地清单 (Refactoring Review Checklist)

> 用于日常开发重构前自检、重构 PR 合并前核对与既有代码质量体检。

---

## 📋 重构核对清单 (Checklist)

### 一、 重构纪律与安全防线 (Discipline & Safety)

- [ ] **1. 外部行为严格不变**  
  - **判定依据**：本次变更所有输入输出契约、HTTP 响应结构、错误码、副作用与原有系统严格 100% 一致。  
  - **违背代价/风险**：改变了外部行为即变成“伪重构”，极易引入破坏性改动并导致上下游调用方线上崩溃。

- [ ] **2. 提交纯粹性与两顶帽子隔离**  
  - **判定依据**：Git 提交记录与 PR 中严禁混入任何新业务功能、新字段或无关 Bug 修复，纯粹为代码结构改善。  
  - **违背代价/风险**：混合提交导致 Code Review 无法理清脉络；线上故障时无法通过 `git revert` 单独回滚。

- [ ] **3. 自动化测试防护网全绿验证**  
  - **判定依据**：重构目标代码段在重构前具备单元测试或集成测试覆盖，且在重构全过程保持全绿灯通过。  
  - **违背代价/风险**：无测试保护的“裸奔重构”平均会带来 30% 以上的隐蔽回归缺陷。

- [ ] **4. 渐进微步与控制改动规模**  
  - **判定依据**：单次 PR 代码变更控制在 200~300 行以内，每完成一个重构原子手法即通过测试并完成阶段性提交。  
  - **违背代价/风险**：大爆炸式巨型重构必然导致主干合并冲突地狱（Merge Hell），且往往因疲惫导致评审形同虚设。

- [ ] **5. 公共 API 向后兼容性**  
  - **判定依据**：对外暴露的公共类、接口或 SDK 方法未被直接改名或删除；若需升级，已采用 `@deprecated` + 内部委托过渡。  
  - **违背代价/风险**：直接破坏下游消费者的编译或运行时调用，引发跨团队生产事故。

---

### 二、 坏味道治理与结构优化 (Code Smells Resolution)

- [ ] **6. 消除神秘命名与劣质注释**  
  - **判定依据**：所有变量名、函数名精准表达业务意图（做“什么”而非“怎么做”），已剔除解释“代码在干嘛”的废话注释。  
  - **违背代价/风险**：代码充斥缩写或误导性命名，导致后续接盘人员需反复逐行追踪实现才能确认逻辑。

- [ ] **7. 函数单一职责与体积收敛**  
  - **判定依据**：函数行数控制在 20~30 行以内，仅处于同一个抽象层次，无长参数列表（入参超过 3~4 个已提炼为参数对象）。  
  - **违背代价/风险**：臃肿长函数隐藏局部临时状态和非预期副作用，单测分支数呈指数级膨胀。

- [ ] **8. 降解嵌套条件与推行卫语句**  
  - **判定依据**：深层嵌套（if/else 超过 2 层）已完全重构为前置卫语句提前 `return`，正常主路径平铺展开。  
  - **违背代价/风险**：深层金字塔嵌套大幅增加认知负荷，边界条件极易在多重分支中被遗漏。

- [ ] **9. 消除重复的分支切换与类型码**  
  - **判定依据**：多处散落的针对同一类型码的 `switch/case` 或 `if-else` 阶梯，已被策略映射表或多态对象统一收敛。  
  - **违背代价/风险**：未来新增一个类型时，必须跨越数十个文件修改分支，漏改一处即引发未处理异常。

- [ ] **10. 消除依恋情结与散弹式修改**  
  - **判定依据**：操作某数据结构的核心逻辑已被搬移（Move Method）至数据所有者类中，调用方不再穿透对象图（迪米特法则）。  
  - **违背代价/风险**：数据与行为割裂，演变为贫血模型；一次简单字段调整需要跨越 5~10 个类同时改动。

---

### 三、 性能与过度工程防御 (Performance & Pragmatism)

- [ ] **11. 防范过度抽象与模式狂热 (YAGNI)**  
  - **判定依据**：未引入当前业务场景不需要的抽象层、空工厂或投机性泛型接口，保持代码尽可能简单直接。  
  - **违背代价/风险**：为了并不存在的未来扩展性，凭空增加 3~5 倍的文件数和跳转成本，系统严重失焦。

- [ ] **12. 热点路径性能与资源释放安全**  
  - **判定依据**：在将临时变量替换为方法查询时，未引入循环内的重复昂贵 I/O 或 N+1 计算；所有卫语句提前退出前已妥善释放锁与连接。  
  - **违背代价/风险**：重构使外观变整洁，但导致线上 QPS 暴跌、高负载下连接池耗尽或死锁。

---

## 📊 评审打分建议

| 得分区间 | 状态判定 | 处理建议 |
| :--- | :--- | :--- |
| **12 项全部通过 (100%)** | 🟢 **卓越 (Excellence)** | 结构健康，无测试与兼容性隐患，可立即合并进入主干。 |
| **通过 10~11 项 (80%~99%)** | 🟡 **合格 (Passable)** | 存在个别小瑕疵（如轻微命名待优化或需拆分小 PR），限期修复后合并。 |
| **低于 10 项 (<80%) 或违背任一安全红线 (1~5)** | 🔴 **不合格 (Blocked)** | 存在伪重构、无测试裸奔或行为变更风险，**严禁合并**，必须回滚或分步重做。 |
